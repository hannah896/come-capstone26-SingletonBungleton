# 로컬 저장

게임 중 ESC 메뉴의 **저장**, **홈**, **종료**에서 저장합니다. 120초마다 자동 저장하며, 로비의 **이어하기 → 저장 목록에서 월드 선택 → 이어서 진행하기**로 불러옵니다. 멀티 월드는 방 이름/인원을 정한 뒤 호스트로 재개합니다. 저장이 실패하면 기존 파일을 유지하고 홈/종료를 중단합니다.

- 경로: `Application.persistentDataPath/Saves/world_<worldId>.json`. 새 월드는 고유 ID를 받아 별도 파일에 저장하고 같은 월드의 수동/자동 저장은 해당 파일을 갱신합니다.
- 월드 개수 제한이나 오래된 파일 자동 삭제는 없습니다. 저장 공간이 부족하면 실패를 알리고 기존 저장을 유지합니다. 기존 파일당 32 MiB 안전 한도와 네트워크 테이블 한도는 유지합니다.
- 이전 파일: 각 JSON의 `.bak` 파일 하나. 원본이 손상되거나 없어도 백업을 검사하여 복구합니다.
- 기존 `slot_0.json`도 저장 목록에 포함되며, 불러온 뒤 저장하면 그 경로를 계속 갱신합니다.
- 목록에는 이름/월드 ID 일부, 저장 시각, 싱글/멀티 여부가 최근 저장 순으로 표시됩니다. 목록은 50개씩 펼치며, 손상/호환 불가 파일은 선택 시 사유를 표시합니다.
- 플레이어 ID는 `PlayerPrefs`의 `Save_PlayerId`에 보관합니다. 이 값을 지우면 기존 개인 저장과 연결되지 않습니다.
- 멀티플레이 파일은 방장 기기에 저장됩니다. 참가자의 마지막 상태는 방장에게 전달되며, 같은 ID로 재참가할 때 복원됩니다. 모든 참가자의 로딩과 저장 응답이 완료되어야 저장합니다.

## 저장 범위

월드 시드/생성 옵션, 게임 시간, 채집·파괴 후 재생성 대기, 건축물과 보관함, 바닥 아이템을 저장합니다. 플레이어 위치/방향, 생존 수치와 지속 피해, 인벤토리의 정확한 슬롯, 장착 장비/내구도, 부패 잔여 시간, 해금한 레시피/진행 중 제작도 포함합니다. 종료한 동안 게임 시간과 부패 시간은 진행하지 않습니다.

멀티 건축물은 호스트의 공유 구조물 상태로 저장하며, 불러오면 구조물·보관함·요리 상태가 모든 참가자에게 다시 복제됩니다. 몬스터·투사체의 순간 상태와 아직 파괴되지 않은 자원의 누적 피해는 저장하지 않습니다. 기존 보관함/요리 UI의 미구현 부분을 완성하는 기능은 포함하지 않습니다.

## 유지보수

- 아이템을 추가하거나 Addressables 이름을 바꾸면 `Tools > Save > Rebuild Item Catalog`로 카탈로그를 갱신합니다. `itemID`와 `recipeID`는 기존 저장이 참조하므로 유지해야 합니다.
- 생성 알고리즘이나 배치 데이터가 바뀌어 기존 배치 ID를 재현할 수 없으면 `GameSaveData.CurrentGeneratorVersion`을 올립니다. 호환되지 않는 파일은 명시적으로 거부합니다.
- 스키마 변경에는 별도 마이그레이션이 필요합니다. 현재 스키마는 버전 1입니다.
- 기존 Fusion 테이블의 용량(파괴 기록 256개, 드롭 256개, 구조물 128개)을 그대로 사용합니다.
- Firebase/계정/클라우드 백업은 후속 작업입니다.

## 검증

EditMode의 `SavePersistenceTests`, `WorldSaveTests`는 파일 교체·백업·무결성·유효성·슬롯·내구도·월드 변경 복원과 월드별 저장 격리, 다수 파일/레거시/백업 목록, 최근 순 정렬, 손상 파일 격리, 취소를 검사합니다.

실제 씬 전환 검증은 초기화가 끝난 빈 Play Mode 세션에서 `SaveFlowSmokeTest.RunAsync(별도의_테스트_JSON_절대경로)`를 실행합니다. 새 월드를 만들고 임시 슬롯으로 저장·로비 복귀·이어하기 후 인벤토리/위치/월드 시간/건축물/드롭을 비교합니다. `Result`로 결과를 확인하고 검증 후 Play Mode를 종료합니다. 기존 게임이 진행 중이면 실행을 거부하며 기존 저장 경로는 덮어쓰지 않습니다. 두 기기의 멀티플레이 검증은 별도로 수행해야 합니다.
